어떻게 세팅한다고 하는가

아래는 공개 문서에 나온 구조 요약이다. 한도 우회 실행 레시피는 적지 않는다. 공통 골격만 말하면, ChatGPT 클라우드는 localhost에 닿지 못하므로 HTTPS 끝점 또는 OpenAI가 호스팅하는 터널이 필요하다.

공식OpenAI Secure MCP Tunnel · developers.openai.com

공식 경로: 아웃바운드 전용 tunnel-client

로컬·사설 MCP를 공용 인터넷에 열지 않고 ChatGPT / Codex / Responses API에 붙이려면, 고객 쪽 tunnel-client가 api.openai.com:443으로 나가는 연결을 유지한다. ChatGPT 플러그인에서 Connection을 Tunnel로 고르고 터널 ID를 고르면 된다. 헬프센터도 “로컬 MCP에 직접 연결은 불가, Secure MCP Tunnel을 쓰라”고 적는다.

코멘트. 폴더+터널 자체는 이미 공식 제품 표면이다. “웹쫀쿠”가 곧 약관 위반이라고 단정하면 이 문서와 충돌한다. 다만 이 공식 경로는 Codex 한도를 아껴 주지 않는다. 손발을 웹에 달아 줄 뿐이다.

원문 확인AIGCDev 튜토리얼 · 2026-08-27 · DevSpace 1.0.8 + Tailscale Funnel

커뮤니티 경로: 로컬 MCP + 공개 HTTPS

반복되는 순서는 이렇다. 허용 폴더를 좁게 정한다. 로컬 포트(DevSpace는 보통 7676)에 MCP를 띄운다. Cloudflare quick tunnel, ngrok, Pinggy, Tailscale Funnel 중 하나로 HTTPS를 만든다. ChatGPT에서 개발자 모드를 켜고 Plugins에 https://호스트/mcp를 등록한다. Owner 비밀번호 또는 OAuth로 승인한다. 새 대화에서 워크스페이스를 연다. 끝나면 터널을 끈다.

AIGCDev는 Funnel이 필요하고 Serve는 안 된다고 못 박는다. ChatGPT 클라우드는 tailnet 밖에 있기 때문이다. DevSpace 이슈 #5에서는 Tailscale Funnel에서 “No Auth”가 실패하고 OAuth가 통과했다는 현장 보고가 있다.

코멘트. 세팅 실패의 대부분은 모델이 아니라 연결 계층이다. URL이 바뀔 때마다 플러그인을 다시 만들고, OAuth 메타데이터가 localhost를 가리키면 웹이 붙지 못한다. 커뮤니티가 “한 번 세팅하면 끝”이라고 말하는 것과 실제 운영 비용이 어긋나는 지점이다.

헬프센터는 앱·전체 MCP·개발자 모드가 Business / Enterprise·Edu 웹에 있다고 적고, Pro는 개발자 모드에서 읽기/가져오기 권한으로 MCP를 쓸 수 있다고 읽힌다. 반면 개발자 커뮤니티(2025-09)와 서드파티 README는 개인 계정에서도 쓰기 도구가 보인다고 가정한다. CodexPro FAQ는 2026년 7월 문서 기준으로 Plus는 커스텀 MCP 티어에 없고, Pro는 write가 없다고 요약한다.

코멘트. “웹에서 파일을 수정한다”는 약속의 병목은 터널이 아니라 계정 정책일 수 있다. 국내 후기가 잘 된다고 해도, 그 계정이 Plus인지 Pro인지 Business인지 구분하지 않으면 재현이 안 된다. 도입 전에 Plugins 화면에 실제로 write / edit이 보이는지부터 보는 편이 맞다.

장단점

사람들이 말하는 장점

  • 웹 대화 UX를 유지한 채 로컬 파일을 다룬다.
  • 이미 내는 Plus/Pro 구독을 코딩 루프에 쓴다.
  • 코드가 벤더 클라우드 작업공간에 통째로 복제되지 않는다고 본다.
  • 허용 폴더·읽기 전용·handoff 모드로 권한 폭을 줄일 수 있다.
  • 공식 Secure MCP Tunnel을 쓰면 인바운드 포트를 안 열어도 된다.

반복되는 단점

  • 웹 대화에도 한도와 응답 시간 제한이 있다.
  • Cloudflare 빠른 터널 URL이 재시작마다 바뀐다.
  • 대화가 몇 턴 가면 개발자 MCP가 꺼지는 보고가 있다.
  • 공개 터널 + 셸 = 링크를 아는 사람의 원격 실행 위험.
  • 심링크·allowedRoots는 OS 샌드박스가 아니다.

코멘트. “웹에서 고친다”와 “공식 터널을 쓴다”를 동시에 노리는 타협안이다. 유형 A 중에서는 약관 표면이 가장 깔끔하다. 대신 신뢰 모델은 ‘이 베타 앱에 내 폴더와 터미널을 준다’로 바뀐다.

웹을 Codex의 모델 슬롯에 꽂기

저장소 한 줄 소개는 “without using Codex quota”다. Codex 작업·도구 하네스는 유지하고, 선택된 모델 턴만 웹 Temporary Chat으로 보낸다. 풀 모드에서는 공식 tunnel-client로 도구 호출을 다시 Codex 태스크에 붙인다.

코멘트. 요청문(“웹에서 파일을 수정”)과 반대 방향이다. 파일 수정은 여전히 로컬 Codex가 하고, 웹은 두뇌만 빌려 준다. 한도 이야기의 진원지이므로 보고서에 넣었지만, 웹쫀쿠의 정의와는 다른 물건이다. 실행 설치 절차는 적지 않는다.

Codex 표면은 할당량을 공유한다

“Local messages and cloud chats share your plan’s usage allowance. Weekly limits may also apply.”

같은 문서는 Codex on the web, CLI, IDE, iOS가 플랜 사용량에 포함되고, ChatGPT Work도 Codex와 같은 가격·크레딧·한도를 쓴다고 적는다. ChatGPT for Excel도 에이전트 한도를 공유한다. 일반 Chat 업로드·이미지·보이스 한도는 별도라는 다른 헬프 문서도 있다.

코멘트. “웹 Codex를 쓰면 CLI 한도가 안 깎인다”는 말은 공식 문서와 충돌한다. 커뮤니티가 실제로 아껴 보인다고 느끼는 지점은 chatgpt.com/codex가 아니라 일반 채팅 + MCP다. 이 구분을 안 하면 실험 설계가 처음부터 틀린다.

공식ChatGPT Work and Codex 헬프 · Developer commands

공식 로컬 폴더는 데스크톱 Codex 쪽

로컬 폴더를 프로젝트에 연결해 읽고 고치는 기능은 데스크톱 앱의 Codex/로컬 프로젝트 문서에 있다. ChatGPT 웹의 슬래시 명령은 데스크톱·CLI 명령 세트를 노출하지 않는다고 한다. 웹에서 로컬을 만지려면 MCP 조립이 된다.

코멘트. 공식 제품만으로도 “폴더를 연결해 웹이 아닌 데스크톱에서 고친다”는 길은 있다. 웹쫀쿠가 존재하는 이유는 그 길이 Codex 한도를 쓰기 때문이다. 불편이 아니라 과금 단위가 동기인 셈이다.

교차 확인DevSpace 보안 모델 · CodexPro SECURITY · AIGCDev · code-server CVE

실질 최대 리스크는 밴이 아니라 노출

  • 공개 터널 URL은 비밀번호처럼 다뤄야 한다.
  • 허용 루트 문자열 비교는 심링크를 따라 새는 보고가 있다.
  • bash는 로컬 사용자와 같은 권한이다.
  • 인증 없는 code-server 공개는 별개 취약점(CVE-2025-47269 등)으로 이미 사고가 난 패턴이다.
코멘트. 제재 토론에 비해 보안 토론이 빈약하다. 계정이 살아 있어도 폴더가 털리면 본전이다. 공식 tunnel-client가 커뮤니티 quick tunnel보다 나은 이유는 한도가 아니라 인바운드 면을 안 열어서다.
